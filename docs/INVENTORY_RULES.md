# 재고 · 대여 시스템 규칙

최종 점검: 2026-07-29 · 대상 DB: Cloudflare D1 `lotte-db`

---

## 1. 핵심 원칙 — 재고는 "저장"되지 않는다

**`inventory_history` 테이블이 재고의 유일한 진실 공급원(single source of truth)입니다.**
재고 수량은 어디에도 저장되지 않고, 매번 이력을 합산해서 만들어집니다.

`backend/src/index.js:126`
```sql
SELECT code, color, size, SUM(qty) AS qty
FROM inventory_history
GROUP BY code, color, size
```

이 한 줄이 전부입니다. 따라서:

- **재고를 바꾸려면 이력 행을 추가해야 합니다.** 재고 값을 직접 고치는 방법은 없습니다.
- **이력 행을 지우면 재고가 즉시 변합니다.** 과거 기록 삭제 = 재고 변경입니다.
- 화면에 보이는 재고가 이상하면, 원인은 **항상** 이력에 있습니다.

### 부호 규약 (반드시 지킬 것)

| type | 부호 | 의미 | 재고 영향 |
|---|---|---|---|
| `IN` | **양수** | 입고 | 증가 |
| `RENT` | **음수** | 대여 반출 | 감소 |
| `RETURN` | **양수** | 반납 | 증가 |
| `ADJUST` | 양수/음수 | 수동 보정 | 증감 |

`SUM(qty)`가 타입을 구분하지 않고 전부 더하므로, **부호가 규약과 다르면 재고가 바로 틀어집니다.**

### 대여현황이 표시되는 조건

`frontend/src/pages/RentalPage.tsx:38`
```js
type === 'RENT'  AND  자신의 id를 ref_id로 가리키는 RETURN 행이 없음
```

**두 조건을 모두 만족해야 "대여중"으로 뜹니다.** 그래서:

- `type`이 `RENT`가 아니면 (예: `OUT`) → **재고는 깎이는데 대여현황에는 안 보입니다.**
- 반납은 반드시 `ref_id`에 원본 RENT 행의 `id`를 넣어야 짝이 맞습니다.

## 2. 정상 동작 흐름

| 작업 | 화면 | API | 생성되는 이력 |
|---|---|---|---|
| 상품 등록 | 상품등록 | `save_product` | 없음 (products 테이블) |
| 재고 입고 | 상품등록 → 재고 매트릭스 | `save_history` | `IN` 양수 |
| 대여 반출 | 상세 → 대여 | `save_history` | `RENT` 음수 |
| 반납 | 대여현황 → 반납 처리 | `save_history` | `RETURN` 양수 + `ref_id` |
| 대여 취소 | 상세 → 대여 삭제 | `save_history` | `RETURN` 양수 + `ref_id` |

재고 매트릭스의 숫자는 **"지금 몇 개를 새로 넣을지"** 이지 총량이 아닙니다.
`RegisterPage.tsx:423` 주석대로 입력한 수량만큼 `IN` 이벤트가 새로 쌓입니다.

## 3. 절대 하지 말 것

### `backfill_history.js` 재실행 금지

`backfill_history.js:11`이 `frontend/public/data.json`의 `stockMap`을 읽어 `IN` 이벤트를 만듭니다.
그런데 이 `stockMap`은 **2026-07-06 이후 갱신되지 않는 동결 데이터**입니다 (212코드 / 5,539개).

- 편성표 스크래퍼가 `items` 키만 덮어쓰고 나머지는 보존하므로 영원히 안 바뀝니다.
- 앱은 이 값을 읽지 않습니다 (죽은 데이터).
- **재실행하면 3주 묵은 재고 5,539개가 통째로 다시 입고됩니다.**

### `inventory` 테이블에 직접 쓰기 금지

구조상 존재하지 않습니다. 파생 값이므로 쓸 대상이 없습니다.

### 대여를 `OUT` 타입으로 만들지 말 것

재고만 깎이고 대여현황에 안 나타나 **반납 처리가 불가능해집니다.**

## 4. 알려진 문제 (2026-07-29 기준)

### 🔴 즉시 조치 권장

**① 대여현황에 안 보이는 대여 6건 — 재고 6개가 묶여 있음**

앱이 07-23 이전에 대여를 `RENT`가 아니라 `OUT`으로 기록했습니다. 그 6건이 남아 있습니다.

| id | 상품코드 | 컬러/사이즈 | 대여자 | 날짜 |
|---|---|---|---|---|
| 3395 | 12908503 | 네이비/55A | 테스트 | 07-11 |
| 3397 | 12895289 | 그레이/S | 테스트 | 07-19 |
| 3399 | 12908503 | 린넨베이지/55DP | ㅇㅇ | 07-20 |
| 3437 | 12906758 | 블랙/55 | 테스트 | 07-23 |
| 3438 | 12906758 | 화이트/55 | 테스트 | 07-23 |
| 3439 | 12906758 | 토피브라운/55 | 테스트 | 07-23 |

전부 미반납 상태이고 **UI로는 반납할 수 없습니다.** 대여자가 대부분 `테스트`라 시험 데이터로 보입니다.
→ 실제 대여면 `type`을 `RENT`로, 시험 데이터면 이력을 삭제해야 합니다.

**② 테스트 데이터가 프로덕션 재고에 포함됨 — 30개**

`12838788`에 사이즈가 `테스트`인 항목이 색상 3종 × 10행씩 총 30개 입고돼 있습니다 (id 3365~3394).

**③ 저장 실패가 성공으로 표시됨**

`backend/src/index.js:495`가 실패를 **HTTP 200**으로 반환하는데, `useAppStore.ts:77`이 응답 본문을 확인하지 않습니다.
axios는 200에 예외를 안 던지므로 **"저장되었습니다" 알림이 뜨고 실제로는 저장되지 않습니다.**

### 🟡 개선 권장

**④ 재고 초과 대여 방지 없음**

`DetailPage.tsx:296` `handleSubmitRental`이 현재 재고를 확인하지 않고 `RENT`를 생성합니다.
보유 수량보다 많이 대여하면 **재고가 음수**가 됩니다. (현재 음수 재고는 0건)

**⑤ 이력 삭제 수단이 앱에 없음**

잘못 등록한 `IN`(위 ②번 같은 경우)을 되돌릴 방법이 UI에 없습니다. `RETURN`으로 상쇄만 가능한데 의미가 맞지 않습니다.

**⑥ `update_history`가 `type`을 수정 못 함**

`backend/src/index.js:571`이 `qty`, `date`, `note`만 UPDATE합니다.
`type`을 고치려면 D1에 직접 SQL을 실행해야 합니다.

**⑦ 인코딩 깨진 이력 2건**

id `3449`, `3450` — `actor`와 `note`가 깨져 있습니다. curl 테스트 흔적입니다.

**⑧ 상품정보 없는 재고 1건**

`12888560` — 재고 20개는 있는데 상품 마스터가 없어 "기본 정보가 없는 상품"으로 표시됩니다.

**⑨ 백업이 재고를 담지 않음**

`backup.js`는 `rentals`, `outfits`, `notes`, `supplies`만 저장합니다. 그런데
- `rentals`는 API 응답에서 사라진 키라 **항상 건너뜁니다**
- **`inventory`, `history`, `products`는 백업 대상이 아닙니다**

실질적 안전망은 **Cloudflare D1 Time Travel(보존 30일)** 입니다. 그 밖의 시점은 복구 수단이 없습니다.

## 5. 사고 이력

**2026-07-23 · 이력 이관(`3eff175`) 시 상품 1건 소실**

`12912518` (사만사타바사 헤이즈 양가죽 토트백, 16개)이 상품정보·재고 모두 사라졌습니다.

- 원인: 백필이 **동결된 07-06 `stockMap`** 을 기준으로 이력을 생성
- `12912518`은 07-06 이후 등록돼서 그 스냅샷에 없었음 → 이력 0건 → 파생 재고 0
- 2026-07-29 사용자가 직접 재등록하여 복구 완료 (id 3453~3456)

**2026-07-29 · 이관된 대여 18건이 대여현황에서 누락**

백필이 대여를 `type='OUT'`으로 기록해 화면에 표시되지 않았습니다.
`type`을 `RENT`로 변경하여 복구했습니다 (id 3347~3364). `qty`가 이미 음수라 **재고는 변하지 않았습니다.**

> ⚠️ 이때 "대여가 이중 차감됐다"는 오진이 있었습니다.
> 구 시스템은 `stockMap`(총 보유)에서 대여를 **화면에서** 뺐고(`legacy_script.js:927`),
> 신 시스템은 이력으로 합산합니다. **결과는 동일하며 이중 차감이 아닙니다.**
> 이 18건을 삭제하면 재고가 24개 부풀고 반출자 기록이 사라집니다. **삭제 금지.**

## 6. 점검 방법

`backend/` 에서 실행합니다. **`--command` 는 읽기 전용 SELECT만 쓰세요.**

```bash
npx wrangler d1 execute lotte-db --remote --command "SELECT type, COUNT(*), SUM(qty) FROM inventory_history GROUP BY type"
```

정기 점검 항목:

| 점검 | 정상값 | 확인 방법 |
|---|---|---|
| 음수 재고 | 0건 | `SUM(qty) < 0` 인 조합 |
| `OUT` 타입 | 0건 | `type='OUT'` — 있으면 대여현황 누락 |
| 고아 RETURN | 0건 | `ref_id`가 없거나 RENT를 안 가리킴 |
| 중복 반납 | 0건 | 같은 `ref_id`가 2번 이상 |
| 테스트 데이터 | 0건 | `actor`/`size`/`note`에 `테스트`·`QA` 포함 |
| 마스터 없는 재고 | 0건 | `inventory` 코드가 `products`·`data.json`에 없음 |

**복구가 필요하면 D1 Time Travel(30일)** 을 먼저 검토하세요. 단 `restore`는 DB 전체를 되돌리므로
이후 변경분이 전부 사라집니다. 실행 전 반드시 현재 북마크를 기록해 두세요.

```bash
npx wrangler d1 time-travel info lotte-db
```
